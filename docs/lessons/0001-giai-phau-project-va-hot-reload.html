Giải phẫu project & Hot reload

Sau bài này bạn trả lời được một câu mà rất nhiều người viết Flutter cả năm vẫn đoán mò: vì sao có lúc hot reload ăn, có lúc không?

1. Thư mục nào để làm gì

Mở apps/00_hello_flutter ra, bạn sẽ thấy khá nhiều thư mục. Thực tế bạn chỉ sống trong một cái.

Đường dẫnLà gìBạn đụng tới?

Riêng repo này

Bạn sẽ không thấy pubspec.lock hay analysis_options.yaml trong từng app. Đây là pub workspace — cả hai nằm ở thư mục gốc và dùng chung cho mọi app. Nên flutter pub get phải chạy ở gốc repo, không phải trong app.

2. Đường đi từ main() tới pixel

Mọi app Flutter đều đi đúng một con đường. Nhớ con đường này thì phần còn lại của bài tự sáng ra:

void main() {
  runApp(const MyApp());          // ① giao quyền cho Flutter
}

class MyApp extends StatelessWidget {
  Widget build(BuildContext context) {
    return MaterialApp(           // ② theme, routing, localization
      home: const MyHomePage(),
    );
  }
}

class _MyHomePageState extends State<MyHomePage> {
  int _counter = 0;               // ③ STATE — sống ngoài build()

  void initState() { ... }        // ④ chạy MỘT LẦN khi State ra đời

  Widget build(BuildContext context) {
    return Scaffold(...);         // ⑤ chạy LẠI mỗi lần cần vẽ
  }
}

Điểm mấu chốt là ranh giới giữa ③ và ⑤. _counter là một biến nằm trong object State. Object đó tồn tại độc lập với việc vẽ. Còn build() thì bị gọi đi gọi lại liên tục — có thể 60 lần mỗi giây khi đang animation.

3. Hot reload và hot restart khác nhau chỗ nào

Định nghĩa ngắn gọn nhất, và cũng là thứ duy nhất đáng thuộc lòng:

Quy tắc

Hot reload nhét code mới vào máy ảo Dart đang chạy rồi gọi lại build(). Các object State vẫn còn nguyên.

Hot restart vứt sạch mọi thứ và chạy lại từ main().

Hệ quả — suy ra chứ không phải học thuộc

Bạn sửaHot reloadVì sao
Nội dung trong build() Ăn build() được gọi lại ngay
Thêm/sửa widget Ăn Cũng nằm trong build()
initState() Không Đã chạy rồi, không chạy lại
main() Không Hot reload không quay lại tận đó
Giá trị khởi tạo của biến State Không Object State cũ còn sống, giữ giá trị cũ
Biến static / global Không Đã khởi tạo một lần lúc nạp
Đổi enum, đổi kiểu của class Không Đổi hình dạng kiểu, không nhét nóng được
Mẹo thực chiến

Khi thấy “ơ sao sửa rồi mà không đổi?” — đừng nghi ngờ code trước. Bấm R (hot restart) một cái. Rất thường xuyên, code bạn viết đúng, chỉ là hot reload không với tới được chỗ đó.

4. Bốn thí nghiệm — làm đi, đừng chỉ đọc

Chạy lab lên rồi làm lần lượt. Mỗi cái mất chưa tới một phút, và cái số 2 là cái đáng giá nhất bài này. 

cd apps/00_hello_flutter
flutter run -d emulator-5554

Trong terminal đang chạy: r = hot reload · R = hot restart · q = thoát.

  1. Bấm nút + vài lần, rồi sửa chuỗi tiêu đề trong build(), bấm r.

    Kỳ vọng: chữ đổi ngay, và số đếm vẫn giữ nguyên. Đó chính là object State sống sót qua hot reload.

  2. Đổi int _counter = 0; thành = 100; rồi bấm r.

    Kỳ vọng: không đổi gì cả. Giờ bấm R — nhảy lên 100. Dừng lại nghĩ 30 giây xem vì sao, rồi nhìn lại sơ đồ ở mục 3.

  3. Xoá Scaffold, chỉ để lại Text('hi') trần trong MaterialApp.home.

    Kỳ vọng: màn hình đỏ, chữ vàng gạch chân xấu xí. Đọc dòng đầu của lỗi. Đây là cách Flutter báo lỗi — bạn sẽ gặp nó rất nhiều, nên làm quen sớm.

  4. Thêm print('build chạy rồi'); vào đầu build(), bấm R, rồi bấm nút + ba lần.

    Kỳ vọng: dòng đó in ra mỗi lần bấm nút. Đó là bằng chứng build() chạy lại liên tục — lý do vì sao không bao giờ được đặt việc nặng trong build().

Lưu ý

flutter analyze sẽ cảnh báo avoid_print ở thí nghiệm 4. Đúng — print không nên có trong code thật. Ở đây chỉ dùng để quan sát rồi xoá. Hook pre-commit không chặn cảnh báo mức info nên bạn vẫn commit được.
